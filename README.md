# M6 QNX Security Gateway

An experimental network security gateway running QNX OS 8 from USB on a
commercially available GMKtec M6 Ultra mini PC. **Phase 1 — COMPLETE:** the
basic gateway and network-boundary PoC has been validated on real hardware.

The project tests whether an independently managed gateway, using an OS
different from the protected Windows/Linux host, can restrict that host's
network reach while preserving normal Internet access. It is an experimental
proof of concept, not a commercial firewall product.

## What was built

- AMD Ryzen 5 7640HS, two Realtek RTL8125 Ethernet ports, and a TOSHIBA USB drive.
- QNX OS 8, `io-sock`, PF filtering, IPv4 NAT, and DNS redirect.
- Upstream DHCP and a fixed protected LAN; PF verification precedes forwarding.
- An independent network boundary for a protected PC, with local RAM diagnostics.

QNX was selected because of prior embedded/robotics experience, compact
image-based deployment, USB boot, and interest in a heterogeneous OS boundary.
Linux, BSD, or established firewall products could implement a similar
architecture. QNX itself is not a security guarantee.

## Architecture

```text
Internet
   |
Archer C6 — 192.168.0.1/24
   +---- upstream LAN devices
   |
M6 / QNX OS 8
rt1 / upstream / DHCP
   |
PF + NAT
   |
rt0 / 192.168.77.1/24
   |
Protected PC — 192.168.77.2
```

`rt1` and `rt0` are the measured assignments; startup identifies roles by MAC.
`192.168.0.136` was the upstream DHCP address during testing, not a fixed setting.
See [architecture](docs/ARCHITECTURE.md).

## Security and network policy

New upstream-to-protected connections are denied by default. Protected-host
Internet traffic is broadly allowed with stateful filtering. Access toward the
upstream LAN is blocked by default except for explicitly required services such
as the configured upstream DNS path. IPv6 forwarding remains disabled.

PF syntax, loading, enabled state, and rule readback must pass before the
startup gate enables IPv4 forwarding. A separate control image leaves forwarding
disabled despite a valid PF/NAT configuration.

## Limiting Network Reach of AI and Automation

The gateway does not try to determine whether traffic was generated by a human,
malware, automation software, or an AI agent. AI agents and automation are treated
as software operating inside the protected host. The independent gateway limits
the network reachability of that host as a whole, while normal Internet access
remains broadly available.

## Compromised-host and ransomware scenario

If external compromise or ransomware infection occurs, network segmentation can
restrict lateral network reach toward the upstream LAN. This PoC demonstrates
those network controls; it does not prevent local file encryption. Traffic
between devices on the same downstream switch can bypass this boundary.
See the [threat model](docs/THREAT_MODEL.md).

## Real-hardware results

Normal Internet DNS and TCP/443 passed. Both directions of the network boundary
were tested, including an upstream TCP attempt with a real listening destination
and a temporary route: the dedicated PF drop counter increased from **0 to 5**.

The forwarding-off control retained working local diagnostics and valid PF/NAT,
while external TCP and DNS failed with zero forwarding-on requests. The validated
normal baseline was then restored, its USB hash matched, and normal operation
passed again. Conditions and measured values are in [test results](docs/TEST_RESULTS.md).

## Reproduction

This repository contains original control scripts, PF templates, diagnostics,
host tests, and [integration instructions](docs/REPRODUCTION.md). Obtain QNX and
its Generic x86_64 BSP separately, integrate these files into a licensed local
BSP, and use the [test plan](docs/TEST_PLAN.md).

USB holds the gateway boot image separately from the Windows SSD. It is not
claimed to be immutable or tamper-proof. Generated IFS/EFI files, original BSP
files, and QNX runtime components are not distributed here.

See [troubleshooting](docs/TROUBLESHOOTING.md) and [limitations](docs/LIMITATIONS.md).

## Phase 1 — COMPLETE

IPv4 forwarding gate; IPv6 forwarding disabled; forwarding-off control;
restoration to the validated normal baseline and successful operation afterward.
